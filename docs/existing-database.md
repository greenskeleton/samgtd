# Existing database — structure inventory

Source: `.local/current-gtd.sqlite` (gitignored, never committed). Inspected
read-only on 2026-09-10 via a throwaway `rusqlite` tool (not part of this
repo) opened with `SQLITE_OPEN_READ_ONLY`.

This document records **structure only**. It intentionally omits actual task
titles/notes, project titles/notes, and label names (some of which are
personal/system names, not fixed vocabulary).

## Pragmas

| Pragma | Value |
|---|---|
| `user_version` | 0 |
| `application_id` | 0 |
| `foreign_keys` | 1 (enforced) |
| `journal_mode` | `wal` |

WAL mode means a faithful disposable copy of the database requires copying
`current-gtd.sqlite`, `current-gtd.sqlite-wal`, and `current-gtd.sqlite-shm`
together (or checkpointing first) — not just the main file.

## Provenance: externally migrated

A `_migrations` table records 5 migrations already applied by **an existing,
non-Rust application** (filenames only, e.g. `001_init.sql` … `005_domains.sql`,
applied 2026-03-17 through 2026-04-16). This repository did not create this
schema and is not (yet) that schema's migration owner. See
`docs/adr/0003-existing-database-coexistence.md` for how this project's
CRDT/persistence layer avoids conflicting with that ownership.

A `db` table (columns: `name`, `rows`, `cols`, `keys`, `source`) appears to be
a schema-snapshot/introspection artifact generated by the existing
application (its row/column counts do not match live introspection — e.g. it
records `categories` as having 4 columns and 6 rows, while the live schema
has 3 columns and the live count is 5 rows). Treat it as **stale and
non-authoritative**; this project does not need to reproduce or maintain it.

## Identity

Every table uses `INTEGER PRIMARY KEY AUTOINCREMENT` (SQLite rowid aliases).
**There are no UUID columns anywhere.** This is the central compatibility gap
against `AGENTS.md`'s "stable UUID identifiers" requirement — addressed in
`docs/adr/0003-existing-database-coexistence.md`.

Autoincrement gaps exist (e.g. `domains` has ids `1` and `3` but no `2`),
confirming hard deletes have occurred historically — a mapping from local id
to UUID must tolerate gaps and must not assume dense/contiguous ids.

## Tables

### `categories` (5 rows)
Fixed lookup table: `id`, `name` (UNIQUE), `sort_order`. Current rows are
exactly the five categories named in `AGENTS.md`'s "Initial GTD semantics"
(Inbox, Next Actions, Someday/Maybe, Waiting For, Agenda), in that
`sort_order`. `tasks.category_id` is `NOT NULL` — category is required, as
specified.

### `domains` (2 rows, of a possible 3 by id gap)
`id`, `name` (UNIQUE), `sort_order`. Current rows: a "Personal" domain and a
"Work" domain (id `2` is missing — a domain was deleted at some point).
**Not present in `AGENTS.md`'s GTD semantics list.** It is a real,
cross-cutting concept already in use on both `tasks.domain_id` and
`projects.domain_id` (both nullable FKs to `domains.id`, `ON DELETE` not
specified beyond the FK itself). The domain model must account for Domain as
a first-class concept, or explicitly document why it's deferred.

### `labels` (8 rows) + `task_labels` (12 rows)
`labels`: `id`, `name` (UNIQUE), `label_type` (`CHECK IN ('label', 'context',
'tag')`, default `'label'`). All 8 existing rows currently have
`label_type = 'label'`; no row yet uses `'context'` or `'tag'`.

This is how `AGENTS.md`'s "Task has zero or more contexts" is actually
implemented: **not** a dedicated contexts table, but a generalized,
typed Label entity joined many-to-many via `task_labels(task_id, label_id)`
(composite PK, both FKs `ON DELETE CASCADE`). A future Context is expected to
be a `label_type = 'context'` row in this same table, not a separate schema
concept.

### `projects` (13 rows)
`id`, `name` (UNIQUE), `parent_id` (self-FK, `ON DELETE SET NULL`, nullable),
`sort_order`, `title`, `notes` (default `''`), `status` (`CHECK IN
('planned', 'active', 'done')`, default `'active'`), `domain_id` (FK to
`domains.id`, nullable).

Hierarchy is supported by schema but **unused in current data**: all 13
projects have `parent_id IS NULL`. Status in practice only takes `active` or
`done` (no `planned` rows currently exist, though the constraint allows it).

### `tasks` (35 rows)
`id`, `title`, `notes` (default `''`), `status` (`CHECK IN ('TODO', 'DONE')`,
default `'TODO'`), `category_id` (FK, `NOT NULL`), `project_id` (FK, `ON
DELETE SET NULL`, nullable — 11 of 35 tasks have no project), `created_at`,
`updated_at` (both `TEXT NOT NULL DEFAULT (datetime('now'))`), `domain_id`
(FK, nullable — currently populated on all 35 rows despite being nullable).

Note the status values are `TODO`/`DONE` (uppercase), not `AGENTS.md`'s
prose casing ("Todo or Done") — the Rust domain type should treat
`TODO`/`DONE` as the canonical wire/storage values to match existing data
without a needless rename migration.

### `reports` (7 rows)
`id`, `name` (UNIQUE), `description`, `query_json` (small serialized query
definition, ~160–190 bytes each), `sort_order`. Current rows are one per
category plus two aggregate views ("All TODO", "DONE") — a direct match for
`AGENTS.md`'s "saved reports / queries" and "report-specific sort order".
`query_json`'s internal shape was not inspected in this pass (deferred —
not required for the Milestone 001 Task-only vertical slice).

### `_migrations`, `sqlite_sequence`, `db`
Housekeeping/introspection tables belonging to the existing application, not
GTD entities. See "Provenance" above.
